A plain loop costs up to a million steps per operation. With 200,000 operations that is two hundred billion steps. A balanced structure does each operation in about twenty steps, roughly four million in total, which is why we need real data structures.

Our solution has two data structures. Structure A is a segment tree, Structure B is block decomposition. Both answer the same operations. LAZY mode runs on both; STRETCH mode, the best contiguous run, runs on the segment tree only.

A segment tree is a binary tree over the array. Each node owns one segment and stores a summary of it, here the sum. The leaves are single readings, and every parent is built by combining its two children. The tree has about log n levels.

Lazy propagation: when a range add fully covers a node, we update that node's sum and leave a pending note, plus three, saying its children have not been told yet. We do not visit the leaves at all.

Later, a query for the sum of the first two readings walks down into the tagged node. Before going deeper it pushes the pending add into its two children. Now the leaves are correct and the answer is thirteen. Work is only done when someone actually looks.

Find the best stretch.

The second method is stretch: find the contiguous run of readings with the largest sum. A stretch must contain at least one reading, so if every value is negative the answer is the largest single value, not zero. Here the best stretch is three, minus one, five, which sums to seven.

To answer best stretch quickly, each node stores four numbers: the total, the best prefix, the best suffix and the best stretch. A parent is computed from its two children. The best stretch is either inside the left child, inside the right child, or crosses the middle as a left suffix plus a right prefix.

LAZY mode runs on both structures. STRETCH mode runs only on the segment tree, because blocks do not keep prefix and suffix summaries that combine in constant time. We also do not allow range add in STRETCH mode: adding x to every reading changes a run of length k by k times x, so which run wins depends on its length.

LazySegTree

One invariant: push before you go down.

sum, mn already include the node's own lz.lz = what the children have not received yet.
src/structA/lazy_segtree.hpp
apply(node, len, x):    sum[node] += x * len    mn[node]  += x    lz[node]  += xpush(node):  if lz[node] != 0    apply(left,  lz[node])    apply(right, lz[node]);  lz[node] = 0pull(node):    sum[node] = sum[L] + sum[R]    mn[node]  = min(mn[L], mn[R])add(node, l, r, ql, qr, x):    outside → return · inside → apply    else: push → both children → pull
The implementation rests on three small functions. Apply updates a covered node in constant time: sum grows by x times the length, minimum by x, and the pending add by x. Push moves the pending add one level down. Pull rebuilds a node from its children. The add routine uses them in that order, and we always push before going down.
BlockDecomposition

Raw readings stay raw. Pending rides on the block.

01Whole block +5O(1)
02Part of a block +2push first

In block decomposition the raw readings are never touched by a whole-block add. We just change the block's sum, minimum and pending add. The actual value of a reading is raw plus the block's pending. For a partial update we first push the pending into the raw readings, then edit, then rebuild the block's sum and minimum.

pending can't leak into the new value
Point assignment is absolute, so a pending add must not leak into the new value. In the segment tree we turn assignment into a range add of the difference between the new and current value, reusing the same push, apply and pull code. In block decomposition we push the pending add first, then overwrite the raw reading.
U 2 6 (was −4)

Update a leaf. Repair one path.

A point update in STRETCH mode replaces one leaf and re-merges only its ancestors. Changing the second reading from minus four to six updates the leaf, then its parent, then the root. The new root says the best stretch is fourteen, which is three plus six plus five.

The effect of range length at a million readings. For very short ranges block decomposition is fastest because it just scans a few cells. For sums it breaks even around a thousand readings, for minimums around a hundred, and for range add it never wins because partial blocks are pushed and rebuilt. A full-array query costs the tree about four nanoseconds because the root already holds the answer.

Block size matters. Small blocks make the partial edges cheap, which helps short ranges, but give many blocks to walk, which hurts long ranges. Long ranges are best near a block size of a thousand, which is exactly the square root of a million. Our default of floor of root n is a safe compromise.

Our conclusion: for a sensor dashboard with updates, long ranges and the STRETCH mode, choose the segment tree. It is about seven times faster on long ranges and updates and supports stretch. Block decomposition only wins on tiny range queries, memory, and build time, so it is the right choice only for read-mostly workloads with tiny ranges or very tight memory.
